### ⚠️ Corrections to earlier guidance in this file

Instructions below that were true during Track A and are **now wrong**. A session acting on the old version will undo correct work.

- **"Cart + catalog are FINISHED — do not rebuild"** — no longer accurate. `lib/cart/CartProvider.tsx` now delegates its money maths to `lib/domain/pricing.ts`. This fixed a real bug: the original ran `Math.round()` over a **pounds** value, discounting a £145 subtotal by £22.00 instead of £21.75 — overcharging members 25p and able to flip the £50 free-shipping threshold. Do not revert it. The **rules** (15%, ≥£50, qty-0-removes) are unchanged and still correct.
- **Money is integer pence**, not pounds. `lib/domain/money.ts` converts at the boundary. The DB stores `price_pence integer`.
- **`lib/queries.ts` and `lib/supabase/` no longer exist.** Use `lib/db/{client,server,admin,public}.ts`. Repositories replace `queries.ts` in Phase 2, and `public.ts` arrived with Phase 7a — it is the cookie-free client the public site reads through, and using `server.ts` there instead silently forfeits static rendering.
- **`supabase/migrations/0001_init.sql` no longer exists.** It was never applied and is superseded by `0001`–`0009`.
- **`supabase/seed.sql` no longer exists either.** It was `0001_init.sql`'s partner — its own header said "after `0001_init.sql`" — and was missed when that migration was removed. It inserted `products.price` where the real schema has `price_pence`, so it aborted `supabase start` with `42703`, which meant **the integration and E2E jobs had never once run in CI**: both start a stack, and both died before reaching a test. Deleted. `scripts/seed.ts` is the maintained seeder, reads from the demo modules and is idempotent.
- **The Sanity scaffold is gone** (`sanity/`, `lib/sanity/`, `sanity.config.ts`, `@sanity/*`, `styled-components`). Do not reference it.
- **Stripe is out of scope** for now, by decision. Checkout stays demo-only. The commerce layer manages catalog/inventory/merchandising, not payments.
- **The app is no longer "100% demo data with no env vars."** It needs `.env.local` (see below) and reads a live Supabase project.

**Sections nest, and the shape is row → column → anything.** A container declares a `slot` on its manifest, holds other blocks in `BlockNode.children`, and renders them through a `SectionRenderer` that recurses only for a manifest with a slot. **There are two containers**: `columns` is the row, and it accepts **only** `column` children (`allow: ["column"]`, `direction: "horizontal"`); a `column` accepts anything, including another row. A nested block is selectable, editable, lockable, duplicable and draggable exactly like a root one.

⚠️ **A `columns` row arrives holding two columns rather than empty** — `insertChildren` seeds them — and `column` is `hidden` from the insert menu, because a column outside a row renders but means nothing. **An empty _row_ is publish-invalid by design** (`min: 1`); an empty **column** is deliberately legal, because that is how a row offsets its content or leaves a middle cell open.

**A section can now be dragged from the library onto the canvas**, and dropped at an exact position — including onto a page with nothing on it yet. The drop targets are explicit `gap:N` droppables that exist only while a library item is in flight, so block reordering is untouched. **Click-to-insert is unchanged and remains the accessible path**; the two coexist on one control only because of the drag's 6px activation constraint, which is now load-bearing rather than incidental (see the decisions log).

**Patterns come in two kinds now, and both mean what they say.** A **detachable** pattern copies its blocks into the page at insert time; a **synced** one inserts a single `patternRef` node holding a `_ref`, and the public paths substitute the pattern's published blocks when the page renders — so editing the pattern updates every page using it. The pattern's own `sync_mode` decides which happens, chosen once at creation. The canvas shows a reference as a card rather than as the pattern's content (preview is where the result is shown), and offers **Detach a copy** as the one-way door out. ⚠️ Only **published** patterns expand: the live site reads `published_data` and nothing else, and the card says so when a synced pattern has never been published.

**Every one of the six document types opens in the builder now**, and templates were the last. `/admin/templates` lists, creates, renames and deletes them; `/admin/templates/[id]` is the same builder every other type uses, with an **area switcher** above the canvas. Areas are editor-named — add, rename, remove — and a new template arrives holding one called `main`. ⚠️ **Nothing public renders a template yet**: `template_assignments` resolves one to a record and `resolveTemplateFor` has no caller on the render path. Nothing about a run is destructive: an imported product arrives as a **draft**, an update never rewrites the slug (it is the public URL) and never touches `draft_data` (that is the builder's). `/admin/integrations/jobs/[jobId]` is the review screen — per-item diffs, the feed's own record behind a Payload button, approve/reject, then apply.

### Architecture & patterns to REUSE (don't reinvent)

**Track A (unchanged):**

- **Page content = an ordered `Block[]`** rendered by `components/SectionRenderer.tsx` via `components/sections/registry.ts`; one component per archetype, variants via a `variant` prop.
- **Shared primitives:** `components/ui/*` (`Button`, `Eyebrow`/`MonoLabel`, `clsx`) and `components/store/*` (`ProductCard`, `QtyStepper`, `OrderSummary`, `Field`/`SelectField`). **Reuse `Field` for admin forms** — the sign-in page does.
- **Tokens/layout:** `.container-mg` (1320px, site only — not in `/admin`), the `mg.*` Tailwind tokens, `[data-darkband]`, `.mg-underline`.
- **Chrome is built once** in `app/layout.tsx`.

**Track B (new):**

- **`lib/blocks/`** — one `defineBlock()` manifest per section block, and the only answer to "what fields does this block have, and what is a valid value?". A **pure leaf**: no component references, no I/O (ESLint enforces it). Field descriptors _derive_ the Zod schema — never hand-write a second one. `normalize.ts` is the forgiving render path, `validate.ts` the strict publish path, `binding.ts` the dynamic-content contract with injected sources, `expand.ts` pattern `_ref` expansion, `diff.ts` version comparison. **Adding a block means adding a manifest**; `conformance.test.ts` fails the build otherwise.
- **Publishing is a database transaction, not application code.** `publish` / `unpublish` / `snapshot` / `rollback` / `schedule` / `autosave` are `security invoker` SQL functions (`0010_publishing.sql`, `0011_autosave.sql`), called via `supabase.rpc()`. They write the payload, the revision and the audit event together or not at all. **Never reimplement any of this as a sequence of PostgREST calls** — the autosave bug below is what that costs.
- **Every operation that writes a revision advances `version`** — publish, snapshot, restore _and_ autosave. `revisions` is unique on `(entity_type, entity_id, version)`, so anything writing history without advancing the counter collides with whatever already claimed that number. Do not add a sixth operation that "just records" without taking a version.
- **`lib/db/repositories/`** — the polymorphic document repository plus per-entity helpers. Every function takes the client as its first argument, so the caller decides whether RLS applies. `app/**` and `components/**` are **barred by ESLint** from importing these directly; go through `lib/services`.
- **`lib/domain/`** — pure: types, Zod schemas, business rules. No I/O, no React, no framework. `money.ts`, `pricing.ts`, `permissions.ts` live here.
- **`lib/db/`** — `client.ts` (browser), `server.ts` (caller's session + RLS — use this for admin writes), `admin.ts` (service-role; scripts/jobs/tests only), `database.types.ts` (generated, `npm run db:types`).
- **`lib/services/`** — orchestration + `requirePermission()`. `auth.ts` exposes `getCurrentUser`/`requireUser`/`requirePermission`, cached per render.
- **Layering is enforced by ESLint** (`no-restricted-imports` in `.eslintrc.json`): `app → services → db`; `domain`, `blocks`, `render`, `integrations` are leaves. If the rule complains, the design is wrong.
- **Authorisation is three-layered:** RLS policies (deepest, unbypassable) → `requirePermission()` in services → permission-filtered UI. Permissions are `resource.action` rows in the DB, not an enum.
- **Versioning convention** on every editable entity: `draft_data` / `published_data` / `version` / `status`, with a single polymorphic `revisions` table.
- **`components/admin/`** — the admin application. `ui/*` is its design system (built because the site's own primitives structurally could not serve — see the decisions log); `builder/*` is the canvas, store and panels; `fields/*` is the field→control mapping. That mapping lives here and not in `lib/blocks` because `lib/blocks` is a pure leaf and cannot import React.
- **The builder store is a factory, not a singleton** (`components/admin/builder/store.ts`). zustand + immer, one store per document, held in React context. Undo is a stack of previous tree _references_ — cheap only because immer shares structure and `mapBlocks` never mutates. **Never mutate a tree outside `produce`.** zustand v5 dropped the default shallow comparison, so every selector must be atomic or wrapped in `useShallow`, or it re-renders forever.
- **The builder reaches persistence only through server actions passed in as props.** A server action reference is serializable across the server→client boundary, so `components/admin/builder/` imports nothing from `app/`, the ESLint layering holds trivially, and the store is testable with plain fakes. Same shape as `binding.ts`'s injected sources.
- **Admin server actions return `ActionResult`, never throw.** An exception crossing the boundary reaches the client as a digest with no message. `app/(admin)/admin/_lib/` holds the type and the error translation; it is underscore-prefixed so Next never routes it, and the type lives outside the `"use server"` files because those may export only async functions.

- **`click()` then `page.reload()` is a race, and this repo turns it into data loss.** A button that fires a server action returns immediately; reloading navigates away and can abort the request in flight. `integrations.spec.ts` did exactly that after "Save mappings" and **went red on a docs-only PR with byte-identical application code** (PR #29), having passed on PR #28 ten minutes earlier.   **The defect was one this file had already written down twice and fixed once.** `0018` closed the `is_system` half of it on `pages` and its closing comment named the rest as out of scope. The rest is six tables: a PERMISSIVE `for all` write policy and a PERMISSIVE `for delete` policy on the same table, OR-ed, so `x.write OR x.delete`. Every `*.delete` permission in the catalogue granted and could never refuse.

  ⚠️ **The next-phase entry named three tables and there were six.** It listed `articles`, `products` and `media_assets` — inherited verbatim from `0018`'s closing comment, which had been written from the point of view of the migration that had just touched `pages`. `templates`, `patterns` and `pages` itself have the identical pairing, and `page.delete` was _still_ additive after `0018`. Fixing the three named would have left the item's own headline true. **A scope inherited from an earlier note is a scope worth re-deriving**, because the earlier note was answering a different question.

  **The decision the entry warned about was real and nearly free, and only measuring settled which.** "A migration plus the decision that some role loses access it has today" is accurate and reads far heavier than it is. The grant table:

  | resource                | holds `.write`                      | holds `.delete`             | loses                |
  | ----------------------- | ----------------------------------- | --------------------------- | -------------------- |
  | page, template, pattern | admin, editor                       | admin, editor               | nobody               |
  | product                 | admin, editor, merchandiser         | admin, editor, merchandiser | nobody               |
  | article                 | admin, author, editor               | admin, editor               | author               |
  | media                   | admin, author, editor, merchandiser | admin, editor               | author, merchandiser |

  Four of six tighten nothing. The two real losses are what the seeded role descriptions already promise — `author` is "Writes articles and uploads media; cannot publish", `merchandiser` holds `media.write` for product imagery. And `user_roles` holds **one row**, an `admin`, so the live blast radius was zero. **Price a permissions decision against the grant table, not against the abstraction**; the abstract version is much scarier than the concrete one.

  **The service layer already checked all six, which is the reason to do this rather than the reason not to.** `deleteDocument`, `lib/services/media.ts` and `lib/services/products.ts` each `requirePermission` the right `x.delete` first, so no button in the admin ever got past it and **this migration changes nothing an editor can see**. What it changes is the case where the service layer is not in the path: PostgREST is a public endpoint, the URL and publishable key ship in the client bundle by design, and a signed-in author holds a real JWT. `DELETE /rest/v1/articles?id=eq.…` carries none of the service checks with it. A defence-in-depth fix with no visible behaviour change is the easiest kind to skip and the cheapest kind to ship.

  ⚠️ **One of the seven tables had to be left out, and the policy catalogue could not have told me.** `categories` has the same shape, and it was in scope until the _delete routes_ were read: there are two, on different permissions — `/admin/taxonomy` requires `taxonomy.write`, `/admin/categories` requires `category.delete` — and `0021` widened the write policy to `taxonomy.write OR category.write` deliberately so `author` would keep behaving as it did. A restrictive `category.delete` gate breaks the taxonomy screen for exactly that role. **The tell was in `lib/services/`, not in `pg_policies`.** Recorded as a `KNOWN GAP` test rather than as prose, so the day somebody reconciles the two routes the suite goes red and says so.

  **The probe is the part worth reusing, because it answered in production what the container cannot run.** This container has no Docker daemon, so `npm run test:integration` is unavailable and the RLS suite is written for CI — the loop that cost the nesting spec four rounds. The earlier RLS phase solved this with read and non-destructive write sweeps; this needed something stronger, because the question is _whether a specific actor may delete a specific row_, and that needs an actor.

  The answer was a single transaction, rolled back: insert a throwaway `auth.users` row, a throwaway role holding exactly the permissions under test, a `user_roles` row and a throwaway article; then `set local role authenticated` with `set local request.jwt.claims` to that user's `sub`; then attempt the delete; then `reset role` and count. **`set local` plus `rollback` makes production a safe place to ask a question about production**, and every row involved is one the probe created. Two runs settled it:

  - **write-only actor** (`article.read` + `article.write`): the `update` succeeded and the `delete` was refused, row surviving. The refusal is at DELETE specifically, not the row being hidden — which is the distinction a bare "it failed" cannot make.
  - **delete-holder** (`+ article.delete`): the article went, **and the same actor was still refused a `media_assets` row** it held no media permission on. That second half is what proves the policy is not a blanket `using (false)`, and it costs one extra statement.

  Verified afterwards that nothing leaked: zero probe rows, 53 articles, one `user_roles` row.

  **Also worth knowing: the third characterisation test has now completed the cycle.** `rls.test.ts`'s "still allows deleting an ordinary page" asserted, as the wrong-but-current behaviour, that a `page.write` holder deletes a non-system page — it was the empirical proof of the OR-semantics for `pages`, and it had been passing in CI since `0018`. `0022` inverts it: the same assertion now runs as a `page.delete` holder, because the narrowness of `0018`'s guard has to be shown by an actor that clears `0022`. A new test alongside it proves the two restrictive policies **stack** — a `page.delete` holder is still refused a system page. Three for three, and the technique is unchanged: **write the instruction to invert it inside the test.**

  ⚠️ **The integration half is unrun here and awaits CI**, for the Docker reason above. What was checked statically instead, which is what made the RLS suite green on its first run: `tsc` validated every fixture payload against `database.types.ts`; the CHECK constraint behind `templates.kind` and the NOT NULL columns of `templates`, `patterns` and `categories` were read out of the live catalogue rather than guessed; all fourteen permission keys the new fixtures request were confirmed to exist; and the only triggers on the seven tables are `touch_updated_at`, so the fixture `update` has no hidden dependency.

- **Reordering a column: two bugs wearing one coat.** The note this closes said column reordering was a _missing feature_ — that insertion strips were library-drag-only, so there was no route. That was wrong on both counts, and finding out took a probe rather than a reading: **block-onto-block already reordered columns at the tree level**, and `moveByKey` handled it correctly. What was broken was elsewhere.

  ⚠️ **A forward drag was a silent no-op, for every block, since Phase 4.** `moveByKey` removes the active block and then inserts it at the target's index — but removing it shifts the target back into the index the active just vacated, so `[X, Y]` with X dropped onto Y comes back as `[X, Y]`. Dragging **up** always worked and dragging **down** never did; nothing threw, nothing failed, the block simply sprang back under the cursor. It survived because no test and no E2E ever dragged one block onto another — the suite's drags all come from the library — and because dragging up is what people try first. Fixed by landing _after_ the target when the move is forward within one list.

  ⚠️ **And a column drag resolved to a block inside its neighbour.** `closestCenter` picks the nearest droppable centre, and a column's centre sits close to the centres of the blocks it holds. Passing that key to `moveByKey` nests the dragged column inside its sibling — legal, since a column's slot is unrestricted, and never what the gesture meant. `dropTargetFor` lifts the target back to the dragged block's own list, **scoped to horizontal slots only**: for a vertical list, "drop onto the block inside the container" is the behaviour, not the bug, and it is the only route into a non-empty one.

  **`BlockSlot` gained `direction`, so the row's refusal is declared rather than inferred.** Until now a row showed no strips because `allow: ["column"]` happened to exclude whatever was being dragged. That would have stopped being true the moment something a row _does_ accept were dragged — a column — and the grid would have taken five cells again. Saying "these children sit side by side" is the honest rule.

  **The E2E swaps two columns by dragging**, which is the only place either bug was reachable: it needs a real browser to have a drag handle, a layout and a pointer at once.

  ⚠️ **And that spec failed first time on its own locator, not on the fix.** `getByRole`'s `name` matches a **substring** by default, so `"Drag Column"` also matched the row's own `"Drag Columns — layout"` and three handles resolved where the test asserted two. The assertion was right to refuse — without it the test would have dragged the _row_ onto a column and proved something else entirely. `exact: true`. **The same trap this file already records for `getByLabel`**, which once matched six elements for "Quote"; the lesson did not transfer because the two APIs look unrelated until one of them bites.

- **Columns become real containers, and the bug that forced it.** Reported from the builder: _after dropping the first section into a column, dragging another into a different column does nothing._ It reproduced, and the cause was that **a column was not a thing**. `columns` declared one slot and held a flat list; the grid decided which cell a block landed in by its **index**. Three defects followed from that single fact.

  **There was no per-column drop target.** A drop could only ever say "at index N of the row", never "into this column", so the empty-looking cell was not a droppable at all. Nothing happened because there was nothing there.

  ⚠️ **The canvas's insertion strips were grid items.** They render as siblings of the children, so inside a container they are children of whatever it renders — and a row renders a CSS grid. Probed on the real canvas before changing anything: a two-column row holding two blocks produced `GAP(0), BLOCK, GAP(1), BLOCK, GAP(2)` — **five cells in a two-column grid**, so both blocks sat in the right-hand column on separate rows mid-drag and snapped back on drop. The published output was never affected; `SectionRenderer` passes children straight through.

  **And two blocks could not share a column**, nor could a row have an empty first cell and a filled second. Both are ordinary things to want and neither was expressible.

  **The fix is one shape: row → column → anything.** `column` is a container with its own slot; `columns` narrows to `allow: ["column"]` and seeds two via a new `insertChildren`. Nesting is unchanged — a column's slot is unrestricted, so a column may hold another row.

  **`allow` had been enforced since Phase 2 with no consumer.** `validate.ts` carried the branch and its own test said so outright: _"no shipped manifest can reach this branch"_. `columns` is the first, which is also what makes a pre-change document report itself — a section left directly in a row now validates as _"pullQuote is not allowed in Columns"_.

  **The canvas refuses strips a slot would reject, and that is what keeps the grid intact.** `BlockList` computes `accepts` from the slot's `allow` and the type in flight; a row offers no insertion points during a section drag, so its grid holds only columns. Asserted directly, and the assertion was checked against the old behaviour by disabling the gate — it fails with `['GAP', 'A', 'GAP', 'B', 'GAP']`, which is the reported symptom written as an array.

  **`column` is hidden from the insert menu** — a new manifest flag. It is a real, registered, validated block that means nothing on its own, and `columns` seeds its own; `blockTypes` still lists it, so the conformance suite walks it like everything else.

  ⚠️ **Side-by-side blocks broke the frame chrome, and CI found it on the first run.** A frame's toolbar is absolutely positioned, so it is not bounded by the column it belongs to. Stacked vertically that never mattered; side by side, the **Newsletter's label chip in the second column sat over the Timeline's Duplicate button in the first** and swallowed every click on it — Playwright reporting _"subtree intercepts pointer events"_ and timing out on a button it could see perfectly well. The bar is now `pointer-events-none` with each control opting back in: the label and the issue badge are decorative and should never have been able to eat a click. **Not the same thing as the leaf-only navigation killer** on the content wrapper — that is a different element, and these buttons are its siblings rather than its descendants.

  **The two existing drafts were rewrapped rather than left to rot.** A page and a pattern held `columns` blocks with flat children; nothing published did. Each child became its own column, which reproduces exactly what the grid was already showing — child N was cell N — so the migration is meaning-preserving. Done through the Supabase MCP and read back to confirm.

- **"Should the builder have row support as well?" — asked in the same report, and the answer is that it already does, under another name.** Recorded here because it was answered in conversation and nowhere else, which is how a decision becomes a thing the next session re-litigates from scratch.

  **`columns` _is_ the row.** Since the container fix above, the shape is row → column → anything: a `columns` block is a horizontal band, each `column` child is a cell, and a cell stacks whatever it holds. A separate `row` block would be a second name for the block that already exists, and the two would then disagree about which one a nested layout should use.

  **What a dedicated `row` would genuinely add is not rows — it is _bands_.** A full-bleed background colour or image behind a group of sections, its own vertical padding, and an inner content cap. None of that is about horizontal arrangement, and all of it is expressible as a container block with a slot and a handful of style fields — the `column` manifest is the template for it. **If that is ever wanted, name it `band` or `section`, not `row`**, so the vocabulary keeps meaning what it says.

  ⚠️ **Vertical grouping alone is not a reason to build it.** The canvas already moves a subtree with one drag, and the tree already nests arbitrarily; wrapping two blocks in a container purely to move them together buys nothing the block list does not already do, and costs a level of nesting in every traversal, diff and validation walk.

- **A document can be renamed, and the page-specific version stops being a special case.** `renamePage` was the only rename in the repository, so a pattern's name and key were fixed at creation: getting one wrong meant deleting it and starting again, **losing its revision history with it**. `renameDocument` takes the column names from `DOCUMENT_TABLES` — the title is `title` on a page and `name` on a pattern, the slug is `slug` and `key` — so it serves all six types. `renamePage` now delegates, and the page-specific repository function is deleted rather than left beside its replacement.

  **The error message names the type's own word.** A collision is `23505` on every document table, but being told "that **slug** is taken" about a field labelled **Key** is its own small confusion, so the service keeps a per-type noun. This is the same treatment the page version already gave the code, generalised.

  ⚠️ **`renamePageAction` has existed since Phase 4 with no caller at all.** A page could not be renamed from the admin, and nothing said so — found while generalising this. **It is still not wired, deliberately**: `app/(site)/page.tsx` reads the page with slug `home`, and there is no `/[slug]` route, so `pages` backs exactly one public URL. A rename dialog on the pages list would be a one-click way to make the homepage throw _"No published page with slug home"_ — at build time on Railway and CI too, since the build prerenders it. Wiring it needs a guard on the system page first; the dialog was written, then reverted for exactly this reason.

  **A pattern's key is safe to move, and that asymmetry is the point.** Nothing links to it — it identifies the pattern to editors and to `listInsertablePatterns` — and insertion copies blocks rather than linking, so pages built from a pattern are untouched. A page's slug is an address, an article's is an address, and a product's is one **an import is explicitly forbidden from writing**. The repository writes what it is given; those policies live with the callers that know which case they are in.

  **Patterns had no E2E at all** — the suite reaches pages, articles, products, media, navigation, theme and integrations, and never this. Added with the rename, because the integration test beside it drives the repository with the **service-role client, which bypasses RLS**, so nothing there proves an editor's own session may perform the write. Four specs: create, rename both fields, the collision message, cleanup. ⚠️ The collision case needs a second pattern created by the test itself — **`scripts/seed.ts` writes no patterns**, so an assumed seeded key would have been a test that could only fail.

- **The binding filter editor, and the two defects its own tests found.** `BindingQuery.filter` has existed since Phase 2 and both sources have honoured it since 7c; what was missing was any way to _write_ one, so an editor could retarget a category listing's sort but not its category. No migration and no service change — this is entirely a control.

  **It offers a typed vocabulary rather than a key/value box, and that is the whole design.** Both sources match with `===`, so `lead: "true"` and `issue: 40` match **nothing, silently** — an empty block, no error, nothing in a log, and no way for an editor to tell a mistyped filter from a category that genuinely has no stories. `lib/blocks/bindingFields.ts` declares each source's filterable facts _with the type its rows actually hold_, and the value control is built from that type: a Yes/No select for `lead`, a number box for `price`, text for the rest. The trap is unreachable rather than documented.

  ⚠️ **The conformance test found a real divergence between the two sources on its first run.** `FILTERABLE_FIELDS` is a hand-written description of row shapes that are built in code in two places, so the test walks the demo rows and checks every declared key and type against them. `author` failed: the Supabase source sets it on **every** article row, while the demo source sets it on each category's **lead** row only — its grid cards were transcribed without a byline. So `filter: { author: … }` would have returned different rows depending on which source map the site was handed, which is precisely the property `publicEditorial.test.ts` exists to compare. `author` is not offered, and the file records why. **The two source modules are documented as "identical field for field"; they are not, and now something checks.**

  ⚠️ **The component test found a second one, in the control itself.** Clearing a text filter to retype it made the row **vanish under the cursor** — the key left `filter` (correct: an empty filter must not be stored, since `{ category: "" }` matches nothing) and the row was rendered from `filter` alone, so the box disappeared mid-edit. The test could not type the new value because the input it had just cleared no longer existed. Cleared rows now fall back to a `pending` list and stay on screen; the ✕ is what removes one. **A controlled component needs a stateful test harness** — the first version of that test re-rendered a fixed prop and turned "type 040 into a box holding 039" into `"0390"`, which is a harness bug wearing a component bug's clothes.

  **Changing the source clears the filter, deliberately.** Filter keys belong to a source's row shape, so `category` carried over to `products` is a filter that can never match. Losing a filter on a deliberate source change is the smaller surprise, and the alternative — remembering a filter per source — is state this control does not need.

  **A stored key the vocabulary no longer knows is shown, not dropped.** It renders in the accent colour as "not a field of this source" with its own ✕. Silently discarding part of a saved query on open is how an editor loses work without being told.

- **KEEP READING gets its editor, and the interesting part is one word in an upsert.** `article_relations` has held 159 rows since Phase 7c and had no UI: the seeder wrote the demo's exact trios because module-insertion order is what the article baseline expects, and from that moment nobody could change one. **No migration** — `0004` built the table, `0019` scoped its reads, and everything this needed was already there.

  **An ordered list, not a set, and that distinction is the whole design.** The tags control three inches above it toggles chips, because a tag set has no order. These three have a sequence — left to right across the grid — which is exactly what `article_relations.position` is for. So: add, move up, move down, remove.

  ⚠️ **`setArticleTags` passes `ignoreDuplicates: true`; `setArticleRelations` must not, and the failure mode is silent.** A tag row carries nothing but its own existence, so a conflict really is a no-op. Here the conflicting row holds `position` — and **reordering an already-curated list writes the same pairs with different positions**, which is to say every reorder is _entirely_ a conflict. With `ignoreDuplicates` the save succeeds, the toast says "Saved", the reload shows the old order, and nothing anywhere reports a problem. `tests/integration/articleRelations.test.ts` asserts precisely this case: same three articles, different order, read back.

  **The two constraints are handled in three places, on purpose.** `article_relation_not_self` (`23514`) and the `(article_id, related_id)` primary key (`23505`) are enforced by the table; `normalizeRelatedIds` in `lib/domain` drops the self-reference and collapses duplicates so a direct caller gets a stored list rather than a five-digit code in a toast; and the picker never _offers_ the article itself or anything already chosen, so neither is reachable from the UI at all. The integration test asserts the database still refuses both — because a domain guard that silently covers for a constraint nobody checks is how the constraint quietly stops existing.

  **`KEEP_READING_COUNT` is shared with the public reader.** `publicEditorial.ts` had `.limit(3)` twice, the grid is three across, and the picker caps at three: a curated fourth would have been stored, never rendered, and impossible to explain to whoever chose it. One constant, three consumers.

  **A curated draft is hidden by RLS rather than by the query, and the picker says so.** The related-article select deliberately does not filter status — `0019` scoped `article_relations` so a row is readable only when _both_ ends are published or the caller is staff. So an editor can curate an unpublished piece, see it marked "draft" in the admin, and watch it appear on the live page when it ships. Adding a status filter to the query would be redundant with the policy and would move the rule somewhere it is easier to forget. This is `0019` paying off in a feature written three slices later.

  **And the E2E asserts the property that surprises people: curating needs no publish.** `article_relations` is a live table, not part of `draft_data`, so the save alone changes the public page — the spec curates two articles on an already-published one, reorders them, reloads to prove persistence, then reads the titles back off `/article/<slug>` without touching Publish.

- **The public-site correctness trio — three defects this file had listed separately, fixed together because they are one shape.** Each was a place where the _served HTML_ was wrong while the browser looked fine, which is why all three had survived a suite that drives a real browser.

  **The PDP's soft 404 was the client-component tax.** The whole page was `"use client"` — it holds the gallery index, the stepper and the add-to-bag state — so it could not call `notFound()` and rendered an in-page "we couldn't find that product" screen with a **200**. Both say noindex, so this is untidy rather than wrong; it is recorded because it looks like a bug to the next person to `curl` it.

That window used to render the soft-404 screen. `notFound()` works in a client component — it throws and the nearest boundary catches it — so the race now answers 404 rather than rendering blank.

Setting it `false` would 404 every product published since the last build — a publish that silently does not work, which is precisely the failure mode this project keeps writing down.

  ⚠️ **`/shop`'s fallback was the whole bug, and the Suspense boundary was not the problem.** `useSearchParams` opts its subtree out of prerendering, so **whatever sits in the fallback is what the static HTML contains** — and the fallback was `<ShopHero />` alone. The store shipped a headline and a chip row to anything that does not run JavaScript; the products existed only in the flight payload. Measured before the change rather than assumed: `.next/server/app/shop.html` contained **zero** `href="/product/` occurrences. The fallback now renders the whole store unfiltered, which is what `/shop` with no query string means anyway and what its canonical already claimed. **The page stays `○` static** — reading `searchParams` on the server would render the right grid for every URL and turn the store into a per-request render, trading one defect for a worse one.

Run against the _old_ code it passed, which was wrong: the second `npm run start` had hit `EADDRINUSE` and a **stale server from the fixed build was still answering on 3000**. Killed properly, the same test failed with `Received: 0`. ⚠️ **A test verified against a server you did not restart has verified nothing** — and `reuseExistingServer: !CI` makes this easy to do by accident here.

  **The `product-missing` baseline was recaptured, not deleted.** `/product/the-driving-glove` used to screenshot the PDP's own miss screen; it now screenshots `app/not-found.tsx`, which carries the site chrome and had never had a baseline. Renamed to `not-found`, so the count stays at **16** and the coverage goes up. The evidence that nothing else moved is that the pre-change run failed **exactly two** shots — `/shop`, whose internals were restructured, matched its baseline untouched.

- **Category pages: the first slice built in the right order, and the migration that had been waiting for it.** Every recent feature has been an editor looking for a render path — synced patterns have none, templates have none. Categories were the mirror image: `/[category]` has rendered `categories.published_data` through `SectionRenderer` since Phase 7c, live, with `$bind` listings resolved against `articles` — and there was no way to edit it. So the work was the screen, and the screen was almost entirely reuse.

  **`0014` had already written the release condition.** Its header says `categories` stays off `document_table()` because they "carry the same columns but are not independently publishable, and adding it would imply a UI that does not exist". `0021` moves that line _because_ the UI now exists — a deferral that named its own trigger, which is why this was one migration and not a debate.

  **Four permissions rather than reusing `taxonomy.write`, and the reason is a string.** `publish_document` asserts `has_permission(p_entity_type || '.publish')` — built from the type, so publishing a category needs a permission literally named `category.publish`. Nothing else can satisfy it short of special-casing a name inside a SECURITY INVOKER function every type depends on. The `categories: write` policy was **widened** to accept either permission rather than replaced, so `author` — which holds `taxonomy.write` — loses nothing.

  ⚠️ **`0001`'s role grants had to be replayed.** They read `select key from public.permissions … on conflict do nothing`, so a permission created later reaches no role until those statements run again. Insert four rows and stop, and `admin` would silently not hold them. That is a property of _any_ future permission this project adds, not a quirk of this migration.

  **The test that had to be inverted said the right thing at the time.** `isDocumentType("category")` asserted `false` since Phase 1, citing 0010's allowlist — accurate until this slice. Inverted rather than deleted, the third characterisation test in this repo to complete that cycle after `is_system` (`0018`) and `draft_data` (`0020`).

  ⚠️ **`0021` shipped two defects, and both were caught by tests rather than by reading it. Worth recording individually, because each generalises.**

  **First: `create or replace` replaced the whole body, and the body was copied from the wrong migration.** `document_table()` was rewritten starting from `0014`'s version — which predates `0017` adding `when 'theme' then 'theme_settings'` — so applying `0021` silently _removed_ theme from the allowlist and broke theme publishing everywhere it landed, the live project included. Nothing in the diff looked wrong; the migration reads as an addition. `publicTheme.test.ts` failed with "not a publishable entity type: theme" and named it exactly. **When replacing a function, copy the definition that is currently deployed, not the one in the migration you are imitating** — the header of `0021` now says so in place.

  **Second: the allowlist entry was a promise `publish_document` could not keep.** `categories` never had `created_by`/`updated_by`, unlike every other document table, and `publish_document` writes `updated_by = auth.uid()` in five separate statements → `42703`. Both columns added. **Everything static looked correct**: `document_table()` resolved, the four permissions existed, the RLS policy accepted the write. It took actually publishing a category to find it, which is the whole reason the positive integration test was written alongside the negative ones — _"the sixth document type is rejected"_ would have passed against a completely broken implementation.

  ⚠️ **Two hard-coded counts rotted on the way through CI, in two different suites.** `publishing.test.ts` used `"category"` as its stand-in for "not a publishable type" — `0021` made it real, so the test asserted the opposite of the truth. And `auth.spec.ts` asserted `Permissions — 40 granted`; four new permissions made it 44, so an auth E2E went red on a change that touched no auth. - **A modern Supabase key is not a drop-in, and the SDK is why.** "It is read from the environment, so rotation needs no code change" was in Known issues for phases and was wrong in one specific way, found by doing it: a `sb_secret_…` key went into Railway and every scheduled-publish tick returned **HTTP 500**.

  **The mechanism.** The new keys are not JWTs, and the platform rejects them on `Authorization: Bearer` — it tries to parse one as a token and answers `Invalid JWT`. They belong on `apikey` alone. `supabase-js` sets `Authorization: Bearer <session token ?? the api key>`, and a service-role client never has a session token, so the fallback is always the key itself.

  ⚠️ **The SDK has the guard and does not apply it where we needed it.** `supabase-js` 2.111.0 defines `omitApiKeyAsBearer` and passes it **only** to the Edge Functions fetch — `this.fetch`, which every `.from()` query goes through, keeps the Bearer fallback whatever the key format. That asymmetry is exactly what made the wrong prediction reasonable: reading the SDK suggested REST was fine, and the docs' "Known limitations" section says plainly that it is not. **When the SDK and the docs disagree about a platform rule, the platform is the authority** — the SDK only reveals what its authors assumed.

  **The fix ships before the rotation, deliberately.** `adminFetchFor` returns a `global.fetch` that removes the Authorization header when it carries the key verbatim, and returns `undefined` for a legacy JWT key — a no-op with today's key, so it can merge on its own rather than being wedged into the ops window. It strips only the verbatim key, never a real user token, because removing that would silently escalate a request to the key's privileges.

  **Why it has a unit test rather than an integration one.** The failure appears only when someone edits Railway, and no local or CI run reproduces it: CI's service-role key comes from the throwaway local stack, which is a legacy JWT. The headers _are_ the behaviour, so a fake `fetch` captures them and asserts the rule without a network.
